# Budgetizer Web Application

## Overview
Budgetizer is a personal finance management tool designed to help users track transactions, manage budgets, and visualize cash flow. The web version (`apps/web`) leverages **Firebase** as its backend infrastructure to provide a serverless, scalable, and persistent storage solution, replacing the SQLite database used in the desktop version.

## Firestore Capabilities Used

The application primarily utilizes **Cloud Firestore** for NoSQL document storage. Below is a detailed breakdown of the specific capabilities and patterns employed:

### 1. Cloud Firestore (NoSQL Database)
*   **Document-Oriented Storage**: Data is structured as documents organized into collections. Complex objects (like `Cycle` and `BankTransaction` lists) are serialized into JSON and stored within these documents to minimize read costs.
*   **Simple & Compound Queries**:
    *   **Filtering**: Retrieving records based on specific fields (e.g., `where('cashflow_id', isEqualTo: id)`).
    *   **Sorting**: Ordering results by date (e.g., `orderBy('cycle_date', descending: true)`).
    *   **Indexing**: Relies on Firestore's automatic single-field indexing and requires composite indexes for queries combining equality filters with sort orders.
*   **One-time Reads (`get`)**: The app primarily uses `get()` calls to fetch data on-demand during view initialization, rather than real-time `snapshots()` listeners. This optimizes for lower read counts appropriate for a financial reporting app.
*   **Upsert Operations (`set`)**: Data persistence uses `set()` with merge behavior (saving whole documents) to update budget cycles and settings.
*   **Offline Persistence**: Leverages the default offline support provided by the FlutterCloudFirestore SDK, allowing the app to remain functional and cache data when network connectivity is intermittent.

### 2. Firebase Core
*   **Initialization**: Uses `firebase_core` for platform-specific app initialization.
*   **Configuration**: Relies on `firebase_options.dart` generated by the FlutterFire CLI to manage API keys and project identifiers securely.

## Data Schema

The database schema is designed to map closely to the application's domain entities while optimizing for Firestore's billing model (minimizing document reads).

### Collections

#### `cashflow_cycles`
Stores the core financial data. Each document represents one month (cycle) of activity for a specific account.
*   **Document ID**: Composite key (e.g., `checking_1_2025-01`).
*   **Fields**:
    *   `cashflow_id` (string): Identifier for the bank account (e.g., "Chase Checking").
    *   `cycle_date` (timestamp/string): The start date of the month.
    *   `type` (string): Account type (Checking/Savings).
    *   `data` (map): A large JSON blob containing the full list of `transactions`, `openingBalance`, and `closingBalance` for that month.
        *   *Design Note*: By embedding transactions within the cycle document, fetching a month's history costs only **1 read**, vs 100+ reads if transactions were sub-collections.

#### `reports`
Stores generated reports and analytics configurations.
*   **Document ID**: Report Name (e.g., "Monthly Spending").
*   **Fields**:
    *   `name` (string): Display name.
    *   `data` (map): configuration and cached report parameters.

#### `settings`
Stores key-value pairs for application configuration.
*   **Document ID**: Setting Key (e.g., `theme_mode`).
*   **Fields**:
    *   `value` (string): The stored setting value.

## Access & Security
*   **Authentication**: Currently, the application does **not** implement Firebase Authentication. It operates in effective "single-user" mode assuming the API keys are private or access is restricted via Security Rules allowed IP addresses (or temporarily open rules for development).
*   **Security Rules**: Default rules should be configured to restrict access, as "Test Mode" (open to all) expires after 30 days.
